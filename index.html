CODE CLASSIFICATION] 각 발견 항목을: KEEP / DELETE-CANDIDATE / REFACTOR / REVIEW / RISK / FIX 중 하나로 태깅한다. 특히 찾을 것: - dead code - orphan route - duplicate logic - 오래된 API/컴포넌트 - 미사용 dependency/env - 중복 query - 하나의 책임을 여러 파일/서비스가 나눠 가져 혼란스러운 부분 - 지나치게 강한 coupling - race condition - transaction이 필요한데 없는 부분 - idempotency가 필요한 자동화 - catch 후 무시되는 오류 - 하드코딩 - timezone/date boundary 문제 - 배포환경별 behavior 차이 [5. FRESHNESS + LEGACY BRIDGE AUDIT] ‘수강권 등록 → Main Dashboard에 즉시 반영’ 경로와 ‘Reservation App을 왜 거쳐야 즉시성이 확보되는지’를 함께 추적한다. 다음 후보를 각각 확인: - DB commit 지연 - API cache - Vercel fetch cache / revalidate - client-side query cache - state invalidation 누락 - stale closure/state - polling 주기 - Supabase realtime/subscription 사용 여부와 문제 - service worker/browser cache - Railway API를 거치는 legacy dependency - webhook/job 완료 후 UI 갱신 누락 문제 원인을 증거와 함께 좁히고, A. KEEP AS-IS: 현재 Reservation App 구조를 그대로 유지 B. KEEP & REDEFINE: Reservation App을 공통 operational backend/API/worker로 재정의하고 legacy UI/책임만 정리 C. MIGRATE: 공통 backend로 기능을 이관하고 Reservation App 제거 세 옵션을 비교한다. 비교 기준: 실시간성 / 유지보수 / 배포 복잡도 / 비용 / 장애 범위 / 확장성 / 향후 사내 대시보드 공유 가능성 / 마이그레이션 위험. [6. OUTPUT] A. 현재 시스템 아키텍처 요약 B. 데이터 흐름 맵 C. 자동화 dependency 맵 D. 문제 목록 (심각도 / 수정위험도 / 근거 / 위치) E. 삭제 후보 목록 F. 리팩터링 후보 목록 G. 즉시 수정할 버그/위험 H. 추가 확인이 필요한 항목 I. Reservation App 판정: KEEP AS-IS / KEEP & REDEFINE / MIGRATE J. 그 판정의 근거와 향후 확장 시 위험 K. 안전한 수정 순서 L. 수정 전 필요한 smoke/regression test 목록 아직 확실하지 않은 것은 추정으로 단정하지 말고 ‘확인 필요’로 표시하라.
홈페이지 · 코드 검진
프렌글 Homepage 코드만 집중 점검한다. 목표: 사용자 입력이 정확히 수집되고 Desk/DB로 전달되는지, 오래되거나 중복된 코드가 없는지, 향후 변경 시 Desk 자동화에 예상치 못한 영향을 주는 결합이 없는지 확인한다. 점검: - 모든 route/page/component - 신청 form validation - 중복 신청 방지 - payload shape - API 호출 - error/loading state - 성공했지만 저장 실패하는 케이스 - 중복 submit - legacy endpoint - environment variable - auth/보안 - analytics/추적 코드가 비즈니스 로직을 방해하는지 - dead component/dependency - Desk와 공유해야 할 schema/type이 중복 선언되어 drift 가능한지 출력: 시스템 흐름 / KEEP / DELETE-CANDIDATE / REFACTOR / RISK / FIX / REVIEW. 각 항목마다 파일 경로, 근거, 영향 범위, 권장 다음 행동을 적는다. 수정은 하지 말고 먼저 진단 보고서를 만든다.
DESK · 데이터/자동화 검진
프렌글 Desk 솔루션을 집중 검진한다. Desk 역할: Homepage 데이터를 받아 학생/수강권/세션 데이터를 관리하고 스케줄링하며 출결·전사·Recap·알림톡 등 자동화와 연결되는 핵심 운영 시스템이다. 중점 점검: 1. Student / enrollment / pass / session / schedule 데이터의 source of truth 2. 상태값 정의와 상태 전이 3. 생성/수정/삭제 시 어떤 자동화가 연쇄 실행되는지 4. 같은 비즈니스 로직이 UI/API/cron 여러 곳에 중복돼 있는지 5. 수업 이동/삭제/노쇼/보강/undo 같은 예외 흐름 6. retry와 idempotency 7. race condition 8. DB transaction 필요 구간 9. duplicate row / unique constraint 처리 10. timezone 11. logging과 audit trail 12. 관리자 권한/민감 데이터 노출 13. legacy Reservation Dashboard 의존 14. Vercel/Railway 환경 차이 15. dead/unused/duplicate code 각 기능별로: Trigger → 함수/endpoint → DB write/read → 외부 서비스 → 후속 자동화 → 실패 영향 을 추적하고 dependency map을 만든다. 최종 출력: - 운영상 가장 위험한 10개 - 정리하면 효과가 큰 10개 - 삭제 후보 - 리팩터링 후보 - 지금은 건드리지 않는 게 나은 부분 - 테스트 없이 수정하면 안 되는 흐름 - 권장 작업 순서
AUTOMATION · 엉킴/중복 실행 검진
프렌글 자동화만 따로 점검한다. 대상: 출결 / 전사 / Recap / 알림톡 / Calendar / Meet / 수업 이동·삭제 및 코드에서 발견되는 모든 자동화. 각 자동화마다 다음 표를 만든다: 이름 | Trigger | 조건 | Input | DB Write | External Action | 다음 자동화 | Retry | Idempotency | 실패 처리 | 로그 특히: - 같은 이벤트가 두 번 들어오면 두 번 실행되는가 - 재시도에서 중복 메시지/Recap/수업 생성이 가능한가 - 부분 성공 후 재실행 시 데이터가 꼬이는가 - 실행 순서가 암묵적으로 가정되어 있는가 - cron과 webhook이 같은 일을 하는가 - 실패를 catch만 하고 기록하지 않는가 - 수동 수정이 다음 자동화에 의해 덮이는가 - 삭제 이벤트가 연쇄 삭제/알림을 잘못 유발하는가 결과는 SAFE / WATCH / RISK / FIX 로 분류하고 자동화 dependency DAG를 설명한다. 첫 검진에서는 코드를 수정하지 않는다.
FRESHNESS · Vercel vs Railway 판단
Main Dashboard에서 수강권 등록 직후 최신 데이터가 바로 반영되지 않는 문제를 진단하고 Vercel/Railway 배포구조를 판단한다. 현재: - Main Dashboard: Vercel - Reservation App: Railway - 즉시성이 필요한 backend/worker가 Vercel 쪽에 있어 수강권 등록/리캡 등에서 즉시 반영 문제가 있고, Railway Reservation App이 중간 실시간 계층으로 남아 있다. - 이 중간 계층은 반드시 제거 대상이 아니다. - 앞으로 Main Dashboard 중심으로 사내 대시보드가 늘어날 예정이다. 먼저 다음 경로를 실제 코드로 추적: 수강권 등록 UI → API/action → DB commit → backend response → cache/revalidation → client state → Main Dashboard render 확인: - Vercel fetch/route cache - revalidate 설정 - dynamic/static rendering - client query cache와 invalidation - refresh/polling - Supabase realtime/subscription - API response cache header - browser/service worker cache - DB transaction/commit - Railway legacy API 의존 - 동일 데이터에 서로 다른 endpoint/schema를 쓰는지 원인을 특정한 뒤 아래 3개를 비교: A. KEEP AS-IS — 현재 구조 유지 B. KEEP & REDEFINE — Railway Reservation App을 공통 operational backend/API/worker로 재정의하고 legacy UI/중복 책임만 제거 C. MIGRATE — 공통 backend로 기능 이관 후 Reservation App 제거 평가표: 실시간성 / 단순성 / 배포·롤백 / 비용 / 운영 난이도 / 확장성 / background job / websocket / 장애 격리 / 향후 여러 dashboard의 공통 backend 사용. 최종적으로: - KEEP AS-IS / KEEP & REDEFINE / MIGRATE 중 권장안 - 왜 그런지 - Reservation App이 구조를 단순화하는지 복잡화하는지 - 기존 UI/legacy 부분만 제거할 수 있는 조건 - 향후 Dashboard가 늘어날 때 business logic이 복제될 위험 - 마이그레이션이 필요하다면 단계 - rollback 방법 을 적는다. ‘중간 서비스가 하나 더 있다’는 이유만으로 제거를 권하지 말고, 서비스 책임·중복 로직·장애지점·확장성을 근거로 판단한다.
REFACTOR · 검진 후 안전 정리
이 코드 검진 보고서를 바탕으로 안전한 정리 계획을 만든다. 원칙: - 한 번에 큰 리팩터링 금지. - 기능 변경과 구조 정리를 같은 PR에서 섞지 않는다. - 자동화 핵심 흐름에는 수정 전 테스트/로그를 먼저 확보한다. - 삭제 후보는 import/reference/route/runtime usage를 확인한 뒤 삭제한다. - DB schema/API contract 변경은 소비하는 모든 앱을 확인한다. - 각 단계마다 rollback 가능해야 한다. 우선순위: P0: 데이터 손상/중복 실행/보안/운영 장애 P1: freshness/legacy bridge/중복 로직 P2: dead code/구조 정리/이름 정리 P3: 미관상 리팩터링 출력: PR 단위로 목적 / 수정 파일 / 영향 기능 / 선행 테스트 / 작업 내용 / 검증 방법 / rollback / 다음 단계 를 적는다. 향후 여러 사내 dashboard가 늘어날 것을 고려해 - shared type/schema - common auth - shared API layer - background worker - logging/audit 의 책임 경계를 제안한다.

MASTER · MD 파일 생성 프롬프트

[원칙] - 숫자 데이터 자체는 MD에 저장하지 않는다. - 정책, 정의, 구조, 업무 규칙, 의사결정 근거를 저장한다. - 확인되지 않은 내용을 사실처럼 쓰지 않는다. - 서로 다른 MD에 같은 규칙을 중복해서 쓰지 말고 source of truth를 하나 정한다. - 다른 문서에서 필요한 경우 링크로 참조한다. [생성 대상] MASTER.md BUSINESS_RULES.md CONTENT_RULES.md B2B_RULES.md OPS_RUNBOOK.md DATA_DICTIONARY.md ARCHITECTURE.md DECISION_LOG.md 각 파일마다: 1. 목적 2. 포함할 내용 3. 포함하지 않을 내용 4. 현재 확보된 정보 5. 확인이 필요한 정보 6. 다른 MD와의 연결 을 먼저 설계한 뒤 본문을 작성한다. 특히: - DATA_DICTIONARY.md는 상태값/필드/관계 정의를 명확히 - ARCHITECTURE.md는 서비스별 책임과 데이터 흐름을 명확히 - DECISION_LOG.md는 날짜 / 결정 / 이유 / 영향 / 재검토 조건 형식을 사용한다.
ARCHITECTURE.md · 코드 검진 후

DATA_DICTIONARY.md · 데이터 정의
프렌글 코드/DB를 기준으로 DATA_DICTIONARY.md를 작성한다. 대상: Student / Trial / Enrollment / Pass / Session / Schedule / Attendance / Transcript / Recap / Coach / Teacher 및 발견되는 핵심 엔티티. 각 엔티티마다: - 목적 - key/id - 핵심 필드 - 상태값 enum - 상태값의 정확한 의미 - 생성/변경 주체 - 다른 엔티티와 관계 - source of truth - deprecated/legacy field - 변경 시 영향을 받는 자동화 특히 같은 의미인데 이름이 다른 필드나, 이름은 같지만 의미가 다른 필드를 표시한다. 추측 금지. 코드/DB 근거가 없으면 확인 필요로 둔다.
DECISION_LOG.md · 의사결정 기록
프렌글의 주요 기술/운영 의사결정을 DECISION_LOG.md 형식으로 기록한다. 형식: ## YYYY-MM-DD — 결정 제목 ### 결정 무엇을 결정했는가 ### 배경 왜 이 결정을 검토했는가 ### 선택 이유 왜 이 안을 선택했는가 ### 포기한 대안 어떤 대안을 검토했고 왜 선택하지 않았는가 ### 영향 어떤 서비스/업무가 영향을 받는가 ### 재검토 조건 어떤 상황이 오면 다시 검토할 것인가 --- 예: Reservation App을 즉시 제거하지 않고 KEEP & REDEFINE로 유지하는 경우, Railway backend의 실제 역할과 향후 제거/재검토 조건까지 기록한다.

1. 콘텐츠 훅 생성

프렌글 인스타그램용 영어 콘텐츠를 기획한다. [입력] - 주제: - 핵심 영어 표현: - 타깃: - 사용 가능한 이미지/영상: [목표] 첫 장에서 영어 공부 콘텐츠처럼 보이기보다 “내 얘기 같다 / 이 상황 안다 / 뭐지?”라는 반응을 먼저 만든다. [훅 생성 규칙] 1. 상황형 2개 2. 반전형 2개 3. 감정형 1개 4. “OO 영어로 뭐라고 하지?” 형식은 기본값으로 쓰지 않는다. 5. 한국인이 실제로 입 밖으로 낼 법한 문장으로 쓴다. 6. 너무 교과서적이거나 광고 같은 문장은 제외한다. 각 훅에 대해 - 왜 멈춰볼 만한지 - 어떤 포맷(캐러셀/릴스)에 더 적합한지 - 예상 역할(도달/공유/저장/전환) 을 함께 적어라. 마지막에 가장 강한 훅 1개를 추천하되, 나머지도 버리지 말고 테스트 후보로 남겨라.

2. B2B 후보 수집

프렌글 B2B 제휴 후보 기업을 수집한다. [타깃] 해외영업, 글로벌마케팅, 무역, 해외사업, 개발, 게임, 벤더, 스타트업 등 영어 활용 가능성이 있는 기업. [원칙] - 모수를 넓게 잡는다. - 대행사, 폐업, 개인사업자, 중복은 제외한다. - 연락처가 전혀 확인되지 않는 기업은 최종 후보로 넣지 않는다. - 회사명만 나열하지 말고 홈페이지/기업페이지 근거를 남긴다. [출력 필드] 회사명 / 홈페이지 / 업종 / 규모 추정 / 타깃 이유 / 이메일 / 이메일 유형 / 전화번호 / 담당부서 또는 담당자 / 출처 URL / 확인일 / 검증상태 우선 100개 단위로 수집하고, 이후 별도 검증 단계로 넘긴다.

3. B2B 검증

아래 B2B 후보 기업을 검증한다. [검증 조건] 1. 실제 운영 중인 기업인가 2. 공식 홈페이지 또는 신뢰 가능한 기업 페이지가 있는가 3. 공개 업무용 이메일 또는 전화번호가 확인되는가 4. 연락처 출처 URL을 확보할 수 있는가 5. 중복/폐업/제외업종이 아닌가 [판정] - VERIFIED: 최종 DB 진입 - REVIEW: 기업은 적합하지만 연락처/정보 추가 확인 필요 - REJECT: 폐업, 중복, 연락처 없음, 제외업종 등 [반드시 집계] 후보 수 / VERIFIED 수 / REVIEW 수 / REJECT 수 / 이메일 확인률 / 전화번호 확인률 / 중복 수 / 제외 사유별 수 추측으로 이메일이나 전화번호를 만들지 않는다.

4. 주간 콘텐츠 성과 분석

이번 주 프렌글 콘텐츠 성과를 비교한다. 조회수만으로 평가하지 말고 아래를 함께 본다. - 비팔로워 도달 - 공유/도달 - 저장/도달 - 프로필 방문 - 팔로우 - CTA 반응 콘텐츠를 1) 셀럽/화제형 2) 상황/밈형 3) 실전 표현형 4) 서비스/전환형 으로 분류한다. 각 유형별로 무엇이 먹혔는지, 무엇이 약했는지 분석하고 다음 주 콘텐츠 비중과 테스트할 훅 패턴을 추천한다. 중요: 성과가 낮다고 무조건 포맷을 폐기하지 말고, 그 콘텐츠가 맡은 역할(도달/공유/저장/전환)을 기준으로 평가한다.
